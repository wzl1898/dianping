## 2. 瓶颈分析与原理

### 2.1 系统当前瓶颈

#### 瓶颈一：单线程测试下的 TPS 上限
当前 TPS 较低（33-46）主要是测试方式是顺序单线程，每次请求都包含完整的 HTTP 连接建立 + 请求处理 + 响应解析开销。在真实并发场景下，TPS 会显著提升（连接池复用、IO 并行化）。

#### 瓶颈二：MyBatis-Plus N+1 查询
在 `BlogServiceImpl.toBlogVO()` 中，每个笔记都要单独查询 User 表来获取作者信息：
```java
User user = userMapper.selectById(blog.getUserId());
```
如果有 10 条笔记，就会产生 10 次额外 SQL 查询。这是典型的 N+1 问题。

#### 瓶颈三：Lua 脚本 + RabbitMQ 异步的延迟
秒杀接口虽然响应快（P50=23ms），但这个时间是 Lua 预检 + MQ 发送的时间，真实的订单创建在 MQ 消费者中异步完成。如果 MQ 消费速度跟不上生产速度，订单积压会增大最终一致性延迟。

#### 瓶颈四：Redis 串行操作
`FollowServiceImpl.commonFollow()` 中的 `SINTER` 操作在大集合下可能有性能问题。同样，`BlogServiceImpl.likeBlog()` 中的 Set 操作在高并发点赞时会有竞争。

#### 瓶颈五：GEO 查询 + SQL 回查
`ShopServiceImpl.queryNearby()` 先用 Redis GEO 查坐标，再根据 shopId 回查 MySQL 获取详情，这是两次独立的 I/O 操作。对于大量商户的场景，这个循环查询会成为瓶颈。

### 2.2 架构层面的性能保障

| 机制 | 作用 | 效果 |
|------|------|------|
| **缓存穿透防护** | 空对象缓存 + 布隆过滤器 | 避免恶意 key 直接打到 DB |
| **缓存击穿防护** | 互斥锁（SETNX） | 热点 key 过期时只允许一个线程重建 |
| **缓存雪崩防护** | TTL 随机偏移（±30min） | 避免大量 key 同时过期 |
| **限流防护** | 滑动窗口（ZSet） | 秒杀接口 5 秒内最多 3 次/用户 |
| **异步下单** | Lua + RabbitMQ | 下单响应 < 30ms，削峰填谷 |

## 3. 各模块性能基线（v1 当前版本）

### 3.1 商户查询缓存
- **缓存命中**：~25ms（Caffeine → Redis 任一级命中）
- **缓存穿透**：~200ms（回源 MySQL）
- **改善空间**：Caffeine 本地缓存对热点商户可实现 < 5ms 命中

### 3.2 秒杀系统
- **Lua 预检 + MQ 异步**：P50=23ms，P99=66ms
- **RabbitMQ 消费延迟**：取决于队列堆积量，通常 < 10ms
- **瓶颈**：订单表的 `UNIQUE KEY (user_id, voucher_id)` 在高并发下有插入竞争

### 3.3 附近商户
- **Redis GEO 查询**：~1ms
- **MySQL 回查详情**：~20ms（单条）
- **改善空间**：批量查询可优化到一次 IN 查询

### 3.4 社交互动
- **点赞 SADD/SREM**：~2ms（纯 Redis 操作）
- **Feed 流 ZSet**：~5ms（滚动分页）
- **共同关注 SINTER**：取决于集合大小，建议控制在 1000 以内

## 4. 瓶颈解决方案（v2 规划）

| 瓶颈 | 方案 | 预期效果 |
|------|------|---------|
| N+1 查询 | MyBatis-Plus `selectBatchIds` 批量查用户 | 将 N 次查询降为 1 次 |
| GEO 回查 MySQL | `JSON` 字段缓存商户完整信息到 Redis | 避免回查 MySQL |
| MQ 消费积压 | 增加消费者并发（`max-concurrency: 16`） | 提升消费吞吐 |
| 点赞并发竞争 | `ZINCRBY` + Lua 原子操作 | 避免读写竞争 |
| Feed 流大 V 推送 | 拉模式 + 推拉结合 | 写扩散改读扩散，减少推送量 |
| 单机 TPS 上限 | 分库分表 + 读写分离 | 水平扩展 |

## 6. 测试结论

1. **全部核心接口 100% 可用**，18 个功能测试用例全部通过
2. **秒杀系统响应优秀**：P50=23ms，达到设计目标（< 50ms）
3. **缓存策略有效**：商户详情查询平均 25ms，缓存穿透情况下才会回源 DB
4. **GEO 查询正常**：Redis GEO 功能稳定，距离排序准确
5. **系统架构合理**：异步 MQ、缓存三件套、限流防护等机制均正常工作

### 需要重点关注的优化方向

1. **N+1 查询问题**：`toBlogVO()` 方法中的循环查 User 表
2. **MQ 消费者单线程瓶颈**：默认 concurrency=4，高并发下需要调大
3. **GEO 查询+SQL 回查**：不适合高并发场景，需要缓存商户完整信息
4. **限流参数的合理性**：秒杀接口 5 秒 3 次是保守值，可根据业务调整
